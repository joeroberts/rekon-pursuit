# Rekon Pursuit — macOS Compatibility and Release Matrix

**Purpose:** M0 release-engineering gate for the signed, sandboxed, local-first macOS application defined in the [architecture specification](specification.md). This document records the constraints that must be proven before M1 implementation work starts. It deliberately does **not** invent a pinned Xcode, Swift, package, or SQLCipher version before a clean-build validation selects one.

**M0 policy status:** approved constraints; **not yet released for M1**. M1 may start only when every M0 row marked `Required for M1` has recorded evidence and is accepted by its named owner. A failed row blocks the dependent scope; it must be resolved by selecting a compatible alternative or deferring that scope, never by silently raising the deployment target or adding broader privileges.

## 3. App Sandbox, XPC, and entitlement inventory

Entitlements are deny-by-default. A capability may be enabled only in the first milestone that requires it, and its entitlement inspection is part of that milestone's acceptance evidence. No capability below authorizes a listening service, elevated helper, broad filesystem access, or cross-app data access.

| --- | --- | --- | --- | --- |

| Hardened runtime | Enabled for every shipped executable. Release builds set `get-task-allow = false`; no JIT, unsigned executable memory, DYLD environment, disabled library validation, or debugger exception is permitted. | M1 | Inspect code-signing flags/entitlements in archived app and embedded binaries. | Security/privacy verifier | Required for M1 — pending |

| User-selected read access | `com.apple.security.files.user-selected.read-only` is permitted only when CSV import or manual document attachment ships. ## 4. Dependency, SQLite encryption, and cryptography gate

All selected dependencies must be version-pinned in the resolved package manifest/lock data accepted by CI, license-reviewed, maintained, architecture-compatible, and minimal. Adding a dependency requires the Architect's recorded decision and QA test coverage; no dependency may expand entitlements or introduce a helper/daemon without a separate approved ADR.

| Area | Non-negotiable selection criteria | Required proof before acceptance | Owner | Acceptance status |
| --- | --- | --- | --- | --- |
| Swift packages and build tools | Compatible with selected Xcode/Swift, macOS 14.0, `arm64`, `x86_64`, App Sandbox, hardened runtime, and notarized DMG. License is compatible with private distribution; maintenance/security posture and transitive dependencies are reviewed. | Resolved dependency inventory with version, license, source, hash/revision, owner, purpose, entitlement impact, and security scan result. | Architect + security/privacy verifier | Required for each dependency before use |
| SQLite access layer | Uses parameterized queries, migration support, foreign keys, WAL compatibility with encrypted database, deterministic test injection, and no network/telemetry requirement. | Fresh/migration/transaction/FTS test results on macOS 14.0 universal build. | Architect + QA | Required for M1 — selection and evidence pending |
| SQLCipher or equivalent | Must provide maintained, validated SQLite-at-rest encryption for the selected SQLite version; build as a signed, universal component compatible with App Sandbox/hardened runtime/notarization. It must use a documented cryptographic provider and not require a privileged helper or dynamic runtime download. | On-device test proves a closed database file cannot be opened with stock SQLite; correct key opens it; wrong/missing key fails; WAL, migrations, backup/restore, FTS5, corruption handling, and clean uninstall/reinstall behavior pass. Archive inspection proves the linked binary is signed/universal and uses no prohibited entitlement. | Architect + QA + security/privacy verifier | Required for M1 — selection and evidence pending |
| Key derivation and authenticated encryption | Use platform-supported, reviewed primitives where possible. Blob/backup encryption must be authenticated; database/blob keys and recovery material never enter logs, diagnostics, exports, or analytics. The recovery policy is governed by the local-data lifecycle ADR. | Known-answer and tamper tests; secret-redaction log tests; Keychain-loss/recovery tests when backup recovery is enabled. | Architect + security/privacy verifier | Required for M1 foundation; recovery evidence required before M5 |
| Dynamic code/models | The app must not download or execute unsigned native code. Later local-model runtimes/models require a separate catalog, integrity/signature/hash, license, storage, update, and sandbox compatibility decision before enabling. | Static dependency scan rejects executable downloads; future runtime acceptance tests prove integrity and local-only route behavior. | Architect + security/privacy verifier | Enforced for M1–M5; later feature gate |
| Telemetry and diagnostics | No product telemetry is required for M1–M5. Local diagnostics must redact secrets and sensitive content. Any future telemetry requires a privacy review and opt-in policy. | Log-redaction tests and dependency review. | Privacy owner + QA | Required for M1 — evidence pending |

## 7. M0 acceptance decision

The M0 compatibility/release gate passes only when all M1-required rows above show recorded evidence and acceptance by the named owners, the local-data lifecycle ADR is accepted, and the Planning, TPM, QA, and Delivery Manager gates in `AGENTS.md` have independently approved the implementation plan. The following states are valid and intentionally explicit:

- `Required for M1 — pending`: a prerequisite has not yet been evidenced; M1 cannot start.
- `Deferred by scope`: the capability is prohibited until its named later milestone and separate gate pass.
- `Enforced policy`: the capability is permanently disallowed and must be checked in release inspection.
- `Accepted`: evidence has been recorded in the progress ledger by the named owner(s).

No status may be changed to `Accepted` merely because the project compiles. It requires the stated evidence, independent verification where named, and a delivery-ledger record.
