## Boundary assessment

| High-risk boundary | Evidence reviewed | Decision |
| --- | --- | --- |
| Root-owned recovery modal state and recovery-key exposure | The design and brief retain `ContentView` ownership of every recovery key, sheet, alert, picker, confirmation, and dismissal state. The plan restricts `SettingsView` to local section state, safe display values, and callbacks; it contains no model/store, key text, sheet, alert, route, or persistence owner. `SettingsRootModalPresentation` maps only existing root restore/error state. `SettingsRootModalBindings` clears the root entry before invoking the existing cancellation callback, while failure dismissal invokes only the existing dismissal callback. The planned unit regression uses an empty invalid entry, asserts active-workspace identity across both paths, and never generates or emits a recovery key. | **Accepted for implementation planning.** The Task-2 source review must prove every retained root sheet, alert, binding setter, and Cancel branch uses the required helper or the unchanged existing model call. |
| Protected export: parent binding, source revision, no overwrite, error, cancellation, and active workspace | The existing worker records parent identity and destination identity at review, rechecks both plus the source revision before output creation, and rejects an existing target without replacement. Existing tests cover parent binding, changed-source no-file, and existing-target byte preservation. The new planned cancellation regression creates a review, proves no destination exists before and after `cancelProtectedExport()`, and asserts the current workspace facts are unchanged. The archive-fixture UI test proves the existing empty-entry error is surfaced and cancelable without entering a key. | **Accepted.** Task 1 and Task 2 command lists include each of these lower-layer tests and the new cancellation/no-write regression. A future implementation may not change the established worker behavior in which a failed final write can report that an unusable output may remain. |
| Retained-data purge and expiry | The current purge path selects only workspace-managed eligible archives; it verifies and promotes a replacement before deleting the predecessor, preserves durable blocked/incomplete state on failures, and never touches an external archive. The plan retains the destructive confirmation and visible enrolled purge action. It executes the existing projection/replacement test, wrong-key-before-job-or-lease test, and fixed-boundary expiry test. The UI cancellation test opens and cancels the existing purge sheet without typing a key, then rechecks the same archive summary. | **Accepted.** The test matrix covers successful projection, wrong-key no-write, cancellation presentation, and expiry rather than assuming a happy path. |
| Restore isolation, cancellation, and separate workspace | The existing view model keeps a selected archive security scope until completion/cancellation, resets cancellation state safely, and reports a successful restore as an inactive candidate. The restore service creates a separately keyed candidate and does not change the active-workspace selector. The plan covers awaiting/verification/restore cancellation, failure dismissal, disabled controls, verified inactive restore, selected-separate-workspace relaunch, and return to preserved recovery. The Task-2 root-modal regression asserts cancellation and failure dismissal leave active opportunities unchanged. | **Accepted.** Later review must compare the moved root modifiers with the current bindings and inspect the signed result bundle. |
| Document metadata and recovery-key redaction | `DocumentReferenceSummary` contains only available and relink-required counts; its store query aggregates those counts for active opportunities. The plan passes that summary only, prohibits document objects and path/bookmark/hash/filename/byte-count fields, and makes the UI test inspect panel descendants for seeded metadata sentinels and for actionable controls. The design, brief, plan, and proposed tests prohibit recovery-key values in fixtures, labels, logs, screenshots, attachments, command output, and retained evidence. Fixture host contracts use UUID-qualified temporary roots, a fixed clock, and an explicit proof that personal workspace, keychain, and live support-DB access are disabled. | **Accepted.** Task 3 requires inspection of every retained test attachment and manifest; a plan is not a substitute for that inspection. |

The allowlist prohibits app-route, model, persistence, entitlement, signing, scheme, test-host transport, provider, and network changes. The only planned project-file change is one `SettingsView.swift` registration in each existing app target source phase. Task 3 requires signed Debug app and host builds, strict signature verification, project-diff inspection, and confirmation that result evidence contains no sensitive data. | **Accepted for plan scope.** No signing or network result exists yet, so neither is approved beyond the unchanged baseline and required future verification. |

The final plan’s Task-1 and Task-2 command matrices each run the fixed-clock fixture-host proofs and all required lower-layer contracts: export parent binding, source-revision no-write, no-overwrite, reviewed-export cancellation, purge projection and wrong-key no-write, expiry, restore busy/failure/cancel paths, inactive restore, and separate-workspace relaunch/return. No implementation or test execution was performed in this review because VD2-07 has not started. The required RED and GREEN result bundles remain future acceptance evidence.

## Residual risk and mandatory later checks

- Moving SwiftUI modal modifiers from the private Settings view to `ContentView` can change lifetime or dismissal behavior even if the text and callbacks look identical. A fresh post-Task-2 security/privacy reviewer must inspect the exact binding and modifier diff, then verify the signed focused results and attachments.
- `SettingsArchiveSummary` must continue to retain only its explicitly safe display fields. The implemented source must be checked to ensure no checksum, signing-fingerprint, recovery-key, document, store, or route state crosses into a focused Settings section.
- This plan deliberately does not modify existing export failure semantics, archive recovery behavior, or the three VD2-08 debts. Any change to those areas requires a new design and security/privacy review.
